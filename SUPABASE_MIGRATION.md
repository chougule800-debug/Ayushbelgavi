# Supabase Setup — AYUSH Federation of India, Belagavi

This document describes how the website stores all of its data in **Supabase
(PostgreSQL)**. The application uses a single database layer: the frontend talks
to a small Express backend, which talks to Supabase.

```
FRONTEND (index.html)
    │  reads via anon key + RLS `SELECT`  +  Supabase Realtime
    │  writes via POST / DELETE  /api/:entity
    ▼
BACKEND / API (server.js)     ← service-role key lives here (server-side only)
    ▼
SUPABASE (PostgreSQL)  →  members, announcements, cme, gallery
```

> Membership **certificates** are NOT stored or generated by Supabase. Existing
> certificate files live in a **Google Drive** folder and are shown on the site
> through a Google Drive embedded folder viewer.

---

## 1. Architecture

- **Public reads** use the Supabase anonymous key (public-safe) with Row Level
  Security allowing `SELECT`. The browser caches rows in `localStorage` for
  snappy rendering, but **Supabase is the source of truth**.
- **Admin writes** (`DB.saveDoc`, `DB.deleteDoc`) are proxied through the Express
  backend `/api/<entity>` endpoints. Only the backend holds the **service-role
  key**, which is never exposed to the browser.
- **Realtime** `setupSupabaseRealtime()` subscribes to `postgres_changes` per
  table for live updates.
- No other database, file, or spreadsheet store is used. `localStorage` is used
  only as a client-side cache/UI/session state.

### Database tables

| Table           | Columns (camelCase)                                                                                  | Primary key |
|-----------------|------------------------------------------------------------------------------------------------------|-------------|
| `members`       | `id, name, mobile, qualification, regno, address, transaction, photoBase64, status, source, createdAt, updatedAt, approvedAt` | `id`        |
| `announcements` | `id, title, content, category, createdAt, updatedAt`                                                  | `id`        |
| `cme`           | `id, title, description, date, venue, createdAt, updatedAt`                                           | `id`        |
| `gallery`       | `id, title, imageBase64, createdAt, updatedAt`                                                        | `id`        |

Row Level Security is enabled on all tables. The public `anon` role can `SELECT`;
there are no public write policies (writes go through the backend using the
service-role key, which bypasses RLS).

## 2. Setup

### Prerequisites
- Node.js 18+ (project verified on Node 20.20.2).
- A Supabase project.

### 1. Configure environment
Copy `.env.example` to `.env` and fill in the real values (never commit `.env`):
```env
SUPABASE_URL=your_supabase_project_url
SUPABASE_ANON_KEY=your_anon_key
SUPABASE_SERVICE_ROLE_KEY=your_service_role_key
PORT=3000
```

### 2. Create the database
Run `supabase/schema.sql` in the Supabase SQL Editor. It creates the four tables
(`members`, `announcements`, `cme`, `gallery`), adds the `approvedAt` column,
enables RLS with public `select`, and publishes them for Realtime. It is safe to
re-run.

Approving a member only updates `members.status` to `active` (plus `approvedAt` /
`updatedAt`). It does **not** generate a certificate.

### 3. Install and run
```bash
npm install
npm run dev          # → http://localhost:3000
```

## 3. Environment variables

| Variable                   | Where used           | Notes                                                    |
|----------------------------|----------------------|----------------------------------------------------------|
| `SUPABASE_URL`             | server.js            | Project URL                                              |
| `SUPABASE_ANON_KEY`        | server.js (config)   | Public-safe; served to the browser via `/api/supabase-config` |
| `SUPABASE_SERVICE_ROLE_KEY`| server.js            | **Server-side only** — never exposed to the browser       |
| `PORT`                     | server.js            | Optional; defaults to `3000`                             |

The public frontend config (URL + anon key) is served at `/api/supabase-config`.
The service-role key must never appear in any frontend file.

## 4. API

| Method   | Route                        | Purpose                          |
|----------|------------------------------|----------------------------------|
| `GET`    | `/api/health`                | Health check                     |
| `GET`    | `/api/supabase-config`       | Public Supabase config (URL + anon key) |
| `GET`    | `/api/:entity`               | List a collection                |
| `POST`   | `/api/:entity`               | Create/upsert a record (by `id`) |
| `PUT`    | `/api/:entity/:id`           | Update a record                  |
| `DELETE` | `/api/:entity/:id`           | Delete a record                  |
| `POST`   | `/api/members/:id/approve`   | **Approve** a member (sets `status` to `active`) — no certificate is generated |

Allowed entities: `members`, `announcements`, `cme`, `gallery`.

Membership certificates are served via the Google Drive embedded folder viewer
(no Supabase Storage or certificate table involved).

## 5. Verification

After setup, confirm the CRUD + Realtime path:

- **Public**: homepage, member directory, search, registration, announcements,
  CME, gallery, images, navigation.
- **Admin**: login, members (create/edit/delete), announcements, CME, gallery,
  logout.
- **Database**: create, read, update, delete, and realtime — every operation
  should reach Supabase.
- **Realtime**: open two tabs, make a change, confirm the second tab updates via
  `postgres_changes`.
- **Network**: browser devtools should show **no** database requests other than
  the project's Supabase endpoint or the Express API.

---

## 6. Notes

- Admin login is a hardcoded client-side credential check (not a hosted auth
  service). To harden it, move verification behind the backend.
- Images (member photos / gallery) are stored as Base64 in `photoBase64` /
  `imageBase64` columns.
